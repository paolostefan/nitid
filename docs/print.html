Nitid Documentation

Nitid Internals — A Developer’s Guide

Nitid is the name of both the language and its transpiler: it reads .nt source files and translates them into equivalent C code, which you then compile with any C compiler (like gcc or clang).

Think of it as a source-to-source compiler.

The language specifications are here.

The project is written in Rust. If you don’t know Rust, don’t worry — this doc explains the Rust concepts you’ll encounter.

The Pipeline

When you run nitid myfile.nt, the compiler does this, in order:

Source code (.nt)
    │
    ▼
1. LEXER (lexer.rs)            "string" → [Token, Token, ...]
    │
    ▼
2. PARSER (parser.rs)          [Token, ...] → AST (Abstract Syntax Tree)
    │
    ▼
3. SEMANTIC ANALYSIS (sema.rs) Checks types, variable scopes, etc.
    │
    ▼
4. CODEGEN (codegen.rs)        AST → C source code
    │
    ▼
C files (.c) + CMakeLists.txt

Steps 3 and 4 operate on the AST (ast.rs), which is defined in its own file and used by the parser, semantic analyzer, and code generator.

The type system (types.rs) is also shared across steps.

Rust Concepts (for non-Rustaceans)

enum (Rust’s tagged union / sum type)

Like a C enum on steroids. Each variant can carry data:

#![allow(unused)]
fn main() {
enum TokenKind {
  Ident(String),      // carries a String
  IntLit(String),
  Fn,                 // carries nothing (like a plain C enum)
  Plus,
  Semicolon,
  // ...
}
}

You match on it with match:

#![allow(unused)]
fn main() {
match token.kind {
TokenKind::Ident(name) => { /* name is a String here */ }
TokenKind::Fn => { /* this is just a marker */ }
_ => { /* default case */ }
}
}

struct

Like a C struct but with methods defined in an impl block:

#![allow(unused)]
fn main() {
struct Lexer {
  chars: Vec<char>,
  pos: usize,
}

impl Lexer {
  fn new(input: &str) -> Self { /* constructor */ }
  fn peek(&self) -> Option<char> { /* method */ }
  fn advance(&mut self) { /* mutating method */ }
}
}
  • &self = read-only reference to the struct (like a const method in C++)
  • &mut self = mutable reference (can modify the struct)
  • Self = the type of the struct itself

Option<T>

Rust’s way of saying “maybe there’s a value, maybe there isn’t” — like a nullable pointer but safer:

#![allow(unused)]
fn main() {
fn peek(&self) -> Option<char> {
  self.chars.get(self.pos).copied()
}
}

Returns Some(c) if there’s a character, or None if we’re at the end.

Result<T, E>

Either a success value Ok(T) or an error Err(E):

#![allow(unused)]
fn main() {
fn tokenize(&mut self) -> Result<Vec<Token>, String>
}

Callers propagate errors with ?:

#![allow(unused)]
fn main() {
let tokens = lexer.tokenize() ?;  // returns early if Err
}

Box<Expr>

A pointer to heap-allocated data. Used for recursive types (like expressions containing sub-expressions):

#![allow(unused)]
fn main() {
enum Expr {
  BinaryOp {
    left: Box<Expr>,   // points to another Expr on the heap
    right: Box<Expr>,
    op: BinOp,
  },
  IntLit(i128, Span),
  // ...
}
}

If we didn’t use Box, the type would be infinitely large (it’d contain itself).

#[derive(Debug, Clone)]

Auto-implements debug printing and cloning for a type:

#![allow(unused)]
fn main() {
#[derive(Debug, Clone)]
struct Span {
  file: String,
  line: usize,
  col: usize,
}
}
  • Debug lets you print it with {:?}
  • Clone gives you a .clone() method to make a copy

HashMap<K, V>

A hash table (dictionary / map):

#![allow(unused)]
fn main() {
let mut map: HashMap<String, Type> = HashMap::new();
map.insert("x".to_string(), Type::I32);
}

match

Like C switch but way more powerful — can destructure, bind variables, and must be exhaustive:

#![allow(unused)]
fn main() {
match c {
'/' if self.peek_ahead(1) == Some('/') => { /* line comment */ }
'/' if self.peek_ahead(1) == Some('*') => { /* block comment */ }
'+' => { Token::new(TokenKind::Plus, self.span()) }
c if c.is_ascii_digit() => self.read_number(c),
_ => return Err("unexpected character"),
}
}

& and &mut (references)

  • &T = immutable reference (read-only, borrow)
  • &mut T = mutable reference
  • Rust’s borrow checker enforces: either one &mut OR many &, never both at once. This prevents data races at compile time.

File-by-file breakdown

src/types.rs — The Type System

What it does: Defines all the types that Nitid supports and how they map to C types.

#![allow(unused)]
fn main() {
enum Type {
  I8,
  I16,
  I32,
  I64,
  I128,
  I256,   // signed integers
  U8,
  U16,
  U32,
  U64,
  U128,
  U256,   // unsigned integers
  F8,
  F16,
  F32,
  F64,                // floats
  String,
  String16,
  String32,       // strings
  Bool,
  Void,
}
}

Two key methods:

  • Type::from_str(s) — converts "i32" or "int" into Type::I32. Used by the parser.
  • type.c_str() — converts Type::I32 into "int" (the C equivalent). Used by the code generator.

Why it’s its own file: Both the parser (reading types), semantic analyzer (checking types), and codegen (writing C types) need these definitions. Shared single source of truth.

src/ast.rs — The Abstract Syntax Tree

What it does: Defines the data structures that represent parsed Nitid code as a tree. The parser produces one of these, the semantic analyzer walks it, and the code generator walks it again to produce C.

Key structures:

  • Span — file/line/column location info, used for error messages
  • Program — the root node: a package name, list of imports, and list of declarations
  • Decl — either a function declaration (FnDecl) or a variable declaration (VarDecl)
  • FnDecl — function name, parameters, return types, body (a list of statements)
  • Param — a parameter type + one or more names (allows int a, b, c)
  • VarDecl — a variable declaration: optional type, names, optional initializer
  • Stmt — a statement: variable decl, expression, return, block, if/else, while
  • Expr — an expression: literals, identifiers, function calls, binary ops, assignments
  • BinOp — binary operators (add, sub, comparisons, logical, bitwise)

Why enums for Decl, Stmt, Expr: Because a “declaration” can only be one thing at a time — it’s either a function or a variable. Rust enums encode this perfectly: you can’t accidentally mix fields from both.

Rust concept – Box: Expr::BinaryOp has left: Box<Expr> and right: Box<Expr>. This is necessary because Expr is recursive (an expression can contain sub-expressions). Without Box, Rust wouldn’t know how much memory to allocate for an Expr.

src/lexer.rs — The Lexer

What it does: Turns raw source text (a string) into a stream of Tokens.

"fn main() { return 42; }"
    │
    ▼
[Fn, Ident("main"), LParen, RParen, LBrace, Return, IntLit("42"), Semicolon, RBrace]

How it works:

  1. The Lexer struct holds the input characters and a position cursor.
  2. tokenize() loops through characters, skipping whitespace and comments.
  3. For each character, it decides what token to produce:
    • Single-char tokens (;, (, +, etc.) are matched directly.
    • Two-char tokens (==, !=, <=, ->, :=, &&, ||, etc.) peek ahead.
    • " starts a string literal (supports escape sequences like \n, \t).
    • ' starts a char literal.
    • Digits start a number (integer or float, decimal or hex).
    • Letters/underscore start an identifier or keyword.
    • // starts a line comment, /* */ starts a block comment.

TokenKind enum — lists every possible token. Keywords (fn, return, if, while, let, var, true, false, package, import, as) are recognized by is_keyword(). Type names (i32, string, bool, etc.) are recognized by is_type() and produce TokenKind::Type(s) instead of TokenKind::Ident(s).

Rust concept – Vec<T>: A growable array (like std::vector in C++ or ArrayList in Java). Vec<Token> is a list of tokens.

src/parser.rs — The Parser

What it does: Takes the flat list of tokens from the lexer and builds a tree structure (the AST).

Parsing approach: Recursive Descent

Each grammar rule becomes a function. Functions call each other recursively, following the language grammar:

parse_program()
  ├── parse_import()       // import statements
  ├── parse_fn_decl()      // function declarations
  └── parse_stmt()         // statements (also top-level)
        ├── parse_return_stmt()
        ├── parse_if_stmt()
        ├── parse_while_stmt()
        └── parse_expr()
              └── parse_assignment()
                    └── parse_or()
                          └── parse_and()
                                └── parse_bit_or()
                                      └── parse_bit_xor()
                                            └── parse_bit_and()
                                                  └── parse_equality()
                                                        └── parse_comparison()
                                                              └── parse_shift()
                                                                    └── parse_term()
                                                                          └── parse_factor()
                                                                                └── parse_unary()
                                                                                      └── parse_primary()

This chain encodes operator precedence — the deeper the function, the higher the precedence. So parse_term() (add/sub) calls parse_factor() (mul/div), which means * binds tighter than +. Exactly like the C expression precedence table.

  • parse_unary() handles -expr, !expr, ~expr (unary minus, logical not, bitwise not).
  • parse_primary() handles literals, identifiers, function calls, and parenthesized expressions.

Lookahead for declarations: parse_stmt() has a tricky job — it needs to distinguish between:

  • int x; (variable declaration)
  • int x = 5; (variable declaration with init)
  • x = 5; (assignment)
  • x := 5; (declaration with type inference)

It uses lookahead (saves position, reads ahead, restores position) to figure out which case it’s in.

Implicit main function: If there are statements at the top level that aren’t inside any function, the parser wraps them in an implicit fn main(int argc, string argv) -> int { ... }. This means you can write scripts without declaring main.

src/sema.rs — Semantic Analysis

What it does: Walks the AST and checks rules that can’t be expressed in the grammar alone:

  • Variables must be declared before use
  • No duplicate variable names in the same scope
  • Return values must match the function’s declared return types
  • Type compatibility in assignments and binary operations
  • Built-in functions println and printf are recognized

Scopes:

The Scope struct is a chain of hash maps, like nested blocks in C:

#![allow(unused)]
fn main() {
struct Scope {
  vars: HashMap<String, Type>,
  parent: Option<Box<Scope>>,
}
}
  • Scope::new() creates a root scope
  • Scope::child(parent) creates a nested scope — lookups check the current scope first, then walk up to parent
  • When a block ends, the child scope is discarded (variables in it “go out of scope”)

What analyze checks:

For each function:

  1. Records parameter types and return types (builds a function signatures table)
  2. Creates a scope with parameter variables
  3. Analyzes each statement in the function body:
    • VarDecl — checks type compatibility between declaration and initializer, declares variables in scope
    • Expr — infers the expression’s type (recursively)
    • Return — checks the count and (approximately) types of return values match
    • If / While — recursively analyzes sub-blocks (creating child scopes)

Type inference: infer_expr_type() figures out what type an expression produces:

  • Integer literal → I32
  • Float literal → F64
  • String literal → String
  • true/false → Bool
  • Variable reference → the type it was declared with
  • Binary op → result type depends on the operator (== gives Bool, + matches operands)

:= (declare-and-assign): When you write x := 42, the type is inferred from the right-hand side. The analyzer prints a warning but doesn’t error.

Free functions: analyze_var_decl_free and infer_expr_type_free are standalone functions (not methods on Sema). They’re used for both global-level and function-level code. In Rust, you can have functions that are not attached to any struct — they’re just regular functions.

src/codegen.rs — The Code Generator

What it does: Walks the AST and produces C source code as a string. This is the final stage.

Key methods:

  • generate(&program) — the main entry point. Produces:

    • One .c file per input .nt file
    • A CMakeLists.txt for building everything with CMake
    • Copies runtime files (nitid_string.h, nitid_string.c)

  • emit_fn_decl(f, ...) — generates the C function signature. Special case: main gets the standard int main(int argc, char **argv) signature regardless of what the Nitid code said.

Multi-return value handling:

Nitid functions can return multiple values (like Go or Python). C can’t do this natively, so the code generator uses output parameters:

fn foo() -> (int, int) { return 1, 2; }
a, b := foo();

Becomes C:

void foo(int *res0, int *res1) {
    *res0 = 1;
    *res1 = 2;
}
// caller:
int a, b;
foo(&a, &b);

The code generator tracks which functions have multi-return and handles this transparently.

Built-in functions:

  • println(s) → printf("%s\n", s) or printf("literal\n")
  • printf(...) → printf(...) (pass-through)

CMake generation: emit_cmake() produces a minimal CMakeLists.txt that compiles the output C file and the runtime string library together.

Type mapping: infer_expr_type_str() maps Nitid expression types to C type strings:

  • Integer → int
  • Float → double
  • String → nitid_string
  • Char → uint8_t
  • Bool → bool

src/main.rs — The CLI Entry Point

What it does: Ties the pipeline together and handles command-line arguments via the clap library.

#![allow(unused)]
fn main() {
#[derive(Parser)]
struct Cli {
  files: Vec<String>,           // input .nt files
  c_dir: String,                // output C directory (default: "c_src")
  emit_c: bool,                 // print generated C to stdout
  run: bool,                    // also compile and run
  cc: Option<String>,           // C compiler to use
  output: Option<String>,       // output binary name
}
}

Pipeline in main():

  1. Creates c_src/runtime/ output directory
  2. For each input file: a. Read the file b. Parse it → AST c. Semantic analysis d. Code generation → C files
  3. Copies runtime library files (nitid_string.h/.c) into output
  4. Writes all .c files and CMakeLists.txt
  5. If --run is passed: a. Runs cmake -S c_src -B c_src/build b. Runs cmake --build c_src/build c. Runs the resulting binary

Rust concept – mod: The mod declarations at the top (mod ast; mod lexer; ...) tell Rust to include each source file as a module. main.rs is the crate root.

Rust concept – Result<(), String>: The return type of main. Ok(()) means success. Err("message") is an error, which Rust prints and exits with a non-zero code.

Rust concept – clap::Parser: A library that auto-generates CLI argument parsing from struct annotations. #[arg(short = 'o')] means the --output flag also accepts -o.

Build Instructions

Prerequisites

  • Rust toolchain (rustc + cargo). Install from https://rustup.rs/: 
    curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
  • CMake (>= 3.10) and a C compiler (gcc or clang) — only needed if you use --run

Build Nitid

# Debug build
cargo build

# Release build (optimized, faster)
cargo build --release

The binary will be at target/debug/nitid (debug) or target/release/nitid (release).

Run Nitid on a file

# Transpile only — produces .c files in c_src/
cargo run -- samples/hello.nt

# Print generated C to stdout
cargo run -- samples/hello.nt --emit-c

# Or use the built binary directly
./target/debug/nitid samples/hello.nt

Transpile, compile, and run in one step

cargo run -- samples/hello.nt --run

This:

  1. Transpiles to C in c_src/
  2. Runs CMake to build
  3. Executes the resulting binary

Custom output directory

cargo run -- samples/hello.nt --c-dir my_output

C Runtime Tests

The runtime/tests/ directory contains a lightweight C test suite for the runtime library types (nitid_array, nitid_string, nitid_string16, nitid_string32).

Test harness (nitid_test.h)

A minimal, macro-based framework — no external test library required:

MacroPurpose
TEST(name)Defines a test function static void test_name(void)
ASSERT(cond)Fails the test if cond is false
ASSERT_EQ(a, b)Fails if a != b
ASSERT_STR_EQ(a, b)Fails if strcmp(a, b) != 0
ASSERT_NULL(p) / ASSERT_NOT_NULL(p)Nullity checks
RUN_TEST(name)Invokes a test, prints PASS/FAIL, increments global counters
TEST_GLOBALSDeclares _test_passed / _test_failed counters
test_summary()Prints tally and returns exit code

Test structure

Each runtime component has its own .c file:

  • test_nitid_array.c — from_lit (empty, single, multiple), get with negative indexing, type-specific accessors (i32, i64, u8, f64, bool), data independence
  • test_nitid_string.c — construction (from, from_n), clone, at (valid, OOB, empty), append (within capacity, multiple, beyond capacity, large), free (sets null, double-free), code-point access (at_cp — ASCII, multibyte, negative), concat, eq/ne, lt/gt/le/ge
  • test_nitid_string16.c / test_nitid_string32.c — UTF-16 / UTF-32 string operations

Each file exports a register_*_tests() function called from test_main.c, which orchestrates the runner.

Running

cmake -S runtime -B runtime/build -DBUILD_TESTS=ON
cmake --build runtime/build
./runtime/build/tests/nitid_runtime_tests

The BUILD_TESTS=ON flag is off by default — the runtime builds as a static library alone unless tests are explicitly enabled.

Nitid Implementation Roadmap

Current state: ~4200 LOC Rust + ~140 LOC C runtime. Lexer/parser/sema/codegen support scalar types, if/while, multi-return, for loops (C-style + range-based), break/continue, postfix ++/--, source-span errors, no-implicit-cast enforcement, array types (fixed/dynamic), array literals, array indexing (incl. negative), range-based array traversal, structs with methods, enums (typed/untyped with overflow checking), and a nitid_array runtime with bounds-checked access.

Implemented features

Composite Types

FeatureWhat’s involved
ArraysType::TyArray(Box<Type>), Expr::ArrayLit, Expr::Index. Parser handles Type[...], fixed keyword, declaration-level [size]. Sema validates element-type uniformity, non-array indexing, numeric index. Codegen emits nitid_array_from_lit / nitid_array_get. Runtime: nitid_array struct.

Enumsenum keyword, Decl::EnumDecl, Type::Enum. Parser handles enum Name : type { A = val, ... }. Sema validates integral types, value overflow, auto-increment, duplicate variants. Codegen emits typedef enum.
Methods / dot-call syntaxobj.method(args) — parser, sema, and codegen handle . access, method lookup, self pointer receiver. Codegen emits StructName_method(&obj, args).

Phase 2 — Memory Safety

Hardest features. RAII, null-pointer protection, and buffer overflows require runtime bookkeeping.

#FeatureWhat’s involved
2.1Scoped allocation / RAIIIntroduce scope blocks (scope { ... }) where allocations are freed at block exit. Codegen emits alloca or arena with auto-cleanup.
2.2Safe reference typesref T as a language type. Runtime tracks ref count or borrow region. Deref generates bounds check.
2.3Null-pointer preventionOption type pattern: T? cannot be dereferenced without is check (or Rust-style match when that exists).
2.4Buffer overflow runtime checksWire every a[i] access through a bounds check. For arrays: i < len. For strings: i < len. Panic on violation.

Exit criteria: A dangling-pointer or out-of-bounds access produces a runtime panic instead of UB.

Key architectural decisions to make

  1. Transpilation to multi-file C — currently everything goes to one .c. With imports and structs, need one .c per package.

  2. Runtime library design — currently has nitid_string and nitid_array .c/.h pairs. Plan grows to: nitid_i256, nitid_f16, nitid_string16/32, nitid_channel, nitid_mutex, nitid_ref. Consider a single nitid_runtime.h umbrella header.

  3. main auto-wrap — currently best-effort. With packages and imports, this needs to be more deliberate (only wrap dangling code in the file that declares package main or has no main function).

Language Specification

Nitid syntax is largely borrowed from the C language, with a few notable exceptions:

  • no preprocessor directives are allowed;
  • functions have an explicit fn keyword (see Functions);
  • packages.

Types

Base data types follow.

  • boolean type: bool
  • signed integral types: i8, i16, i32 (alias int), i64, i128
  • unsigned integral types: u8, u16, u32 (alias uint), u64, u128
  • float types: f32 (alias float), f64 (alias double)
  • string types: string (UTF-8 string), string16 (UTF-16 string), string32 (UTF-32 string).

Literals

Numbers

All the following are valid Nitid number literals:

123
1 000 000 000
-2.34567
-9.876e-10
0x1000
0XFFFFFFFF
0xff ff ff ff

Identifier names

Identifiers (variable names, function names, package names) must respect this regex:
[a-zA-Z_][a-zA-Z0-9_]*

That is: start with an ASCII letter or an underscore, optionally followed by ASCII letters, underscores and numbers.

No punctuation marks, $,%,£,§.ç, accented letters or non-ASCII chars are allowed.

Legal variable name samples:

  • _
  • a
  • GustavoZen0n3

Variables

Declaration

Variables can be declared by specifying their type before their names, just as in C:

int v;   
i128 largeInt;

Assignment

Variables can be assigned a literal or the value of a variable of the same type:

int a;       // Declare a    
a = 123;     // Assign a    
int b = 456; // Declare and assign b

Declare and assign at once

If there’s no ambiguity, the variable type can be omitted when using := to declare and assign value at once. Otherwise, the parser default to the best guess depending on the context.

s := "Hello, world!"; // UTF-8 string type    
c := 'A';             // 8-bit char/int type    
i := 12;              // assuming 32-bit int type    
precise_i := i64(12); // explicitly asking for a 64-bit int    
j := precise_i;       // j is also a 64-bit int

EBNF Grammar

The following EBNF describes the exact syntax accepted by the current parser implementation. Precedence climbs from low (top) to high (bottom) in the expression hierarchy.

(* --- Top Level --- *)  
Program     = PackageDecl , { Import } , { ( FnDecl | Stmt ) } .  
PackageDecl = "package" , Ident , ";" .  
Import      = "import" , Ident , [ "as" , Ident ] , ";" .  
  
(* --- Functions --- *)  
FnDecl      = "fn" , Ident , [ ParamList ] , [ ReturnTypes ]  
            , "{" , { Stmt } , "}" .  
ParamList   = "(" , [ Param , { "," , Param } ] , ")" .  
Param       = Type , Ident , { "," , Ident } .  
ReturnTypes = "->" , ( "(" , Type , { "," , Type } , ")" | Type ) .  
  
(* --- Types --- *)  
Type        = "i8" | "i16" | "i32" | "i64" | "i128" | "i256"  
            | "u8" | "u16" | "u32" | "u64" | "u128" | "u256"  
            | "f8" | "f16" | "f32" | "f64"  
            | "int" | "float" | "double"  
            | "string" | "string16" | "string32"  
            | "bool" | "void" .  
  
(* --- Statements --- *)  
Stmt        = ReturnStmt | IfStmt | WhileStmt | Block  
            | VarDecl | DeclAssign | ExprStmt .  
ReturnStmt  = "return" , [ Expr , { "," , Expr } ] , ";" .  
IfStmt      = "if" , Expr , "{" , { Stmt } , "}"  
            , [ "else" , ( IfStmt | "{" , { Stmt } , "}" ) ] .  
WhileStmt   = "while" , Expr , "{" , { Stmt } , "}" .  
Block       = "{" , { Stmt } , "}" .  
VarDecl     = Type , Ident , { "," , Ident } , [ "=" , Expr ] , ";" .  
DeclAssign  = [ Type ] , Ident , { "," , Ident } , ":=" , Expr , ";" .  
ExprStmt    = Expr , ";" .  
  
(* --- Expressions (precedence, low → high) --- *)  
Expr        = Assignment .  
Assignment  = Or , [ "=" , Expr ] .  
Or          = And , { "||" , And } .  
And         = BitOr , { "&&" , BitOr } .  
BitOr       = BitXor , { "|" , BitXor } .  
BitXor      = BitAnd , { "^" , BitAnd } .  
BitAnd      = Equality , { "&" , Equality } .  
Equality    = Comparison , { ( "==" | "!=" ) , Comparison } .  
Comparison  = Shift , { ( "<" | ">" | "<=" | ">=" ) , Shift } .  
Shift       = Term , { ( "<<" | ">>" ) , Term } .  
Term        = Factor , { ( "+" | "-" ) , Factor } .  
Factor      = Unary , { ( "*" | "/" | "%" ) , Unary } .  
Unary       = [ "-" | "!" | "~" ] , Primary .  
Primary     = IntLit | FloatLit | StringLit | CharLit  
            | "true" | "false"  
            | Ident , [ "(" , [ ExprList ] , ")" ]  
            | "(" , Expr , ")" .  
ExprList    = Expr , { "," , Expr } .  

whitespace = " " | "\t" ;

(* --- Lexical Elements --- *)  
Ident       = ( letter | "_" ) , { letter | digit | "_" } .  
IntLit      = decimal | hex .
decimal     = digit , { [ whitespace ] digit } .  
hex         = "0x" , hexdigit , { hexdigit }  
            | "0X" , hexdigit , { hexdigit } .  
FloatLit    = digit , { digit } , "." , { digit }  
            | digit , { digit } , [ "." , { digit } ]  
            , ( "e" | "E" ) , [ "+" | "-" ] , { digit } .  
StringLit   = '"' , { ? any char except '"' or '\' ?  
            | escape_seq } , '"' .  
CharLit     = "'" , ( ? any char except "'" or '\' ?  
            | escape_seq ) , "'" .  
escape_seq  = "\\" , ( "n" | "t" | "r" | "\\" | "\"" | "'" | "0" ) .  
  
(* Character classes *)  
letter      = "A" | "B" | ... | "Z" | "a" | "b" | ... | "z" | "_" .  
digit       = "0" | "1" | ... | "9" .  
hexdigit    = digit | "A" | "B" | ... | "F" | "a" | "b" | ... | "f" .

Functions

In Nitid, a function is declared and implemented in the same place, as opposed to the C paradigm of declaration in a .h file and implementation in the corresponding .c file.
A function definition is introduced by the fn keyword.
The function body must be enclosed in curly braces just like in C, Rust, Go, Java…

Function arguments

Function arguments must be specified between parentheses, as a comma-separated list, right after the function name. Functions that do not require arguments can omit argument parentheses.

The type of each arg must be specified before the argument name.
If multiple, consecutive args are of the same type, the type name can be specified before the first one only (just like in Go).

#![allow(unused)]
fn main() {
// Function with different type arguments  
fn funcName(i16 Arg1, string Arg2) {  
  // ...  
}  
  
// Function with same type arguments "grouped"  
fn otherFuncName(int Arg1, Arg2, string StrArg1, StrArg2, StrArg3) {  
  // ...  
}  
  
// Function without arguments: both syntaxes allowed  
fn argLessFunction() {  
  // ...  
}  
  
fn anotherArgLessFunction {  
  // ...  
}  
}

Function return values

Function returning one or more values must have -> right after their name and (optional) argument list.

Functions returning just one value must specify the return type right after ->.

#![allow(unused)]
fn main() {
// Function with one return value  
fn sumFileSizes(string path1, path2, path3) -> i64 {  
    // ...  
}  

// Function without args returning one value  
fn calcGlobalTemperature -> float {  
  // ...  
}
}

Functions returning more than one value must specify all the return types, comma-separated and enclosed in parentheses, as follows.

#![allow(unused)]
fn main() {
// Function with 3 return values  
fn getFileSizes(string path1, path2, path3) -> (i64, i64, i64) {  
    // ...  
}  
  
// Function without arguments returning 3 values  
fn getPiggiesName -> (string, string, string) {  
  // ...  
}  
}

Function calls

Functions -even the ones taking no args- must be called by specifying their name followed by parentheses, optionally enclosing arguments.

#![allow(unused)]
fn main() {
// Call a func with no args  
argLessFunction();  
  
// Call a func with args  
funcName(42, "No stairway to heaven");  
}

Special functions

The only special function name handled by Nitid is main.
If a package contains a function named main, that package will be built as a CMake executable target and the executable entry point will be its main function.

Arrays

Arrays in Nitid are almost the same as C, with a few differences.

  1. Size: arrays can be resized dynamically in a transparent way. If you prefer not to opt in, just declare them fixed-size with the fixed keyword.
  2. Bounds checking: any array access is checked, out-of-bounds accesses are prevented -depending on context- at compile time and/or at runtime.

Declaration

A fixed-size array of 35 ints can be declared as follows:

fixed int a[35];     // C-style
b := fixed int[35];  // Implicit var declaration
c := fixed [35 int]; // Alternate syntax declaration

The same arrays can be dynamically sized by omitting the fixed keyword. That way they will be resized on demand or when an append operation is called.

int a[35];
b := int[35];
c := [35 int];

Literals

Array literals can be specified in curly braces, as in C. An array literal can be declared with or without specifying its size, as follows:

// Explicit size
fixed int a[3] = {1};           // Remaining items will be initialized to 0
b := fixed int[300]{1, 2};      // Elements 2..299 will be zeroed out
c := int[100]{0, 1, 200};       // Elements 3..99 will be zeroed out
d := [3 int]{1, 2, 3, 4, 5, 6}; // <- Error! Size is 3, literal won't fit

// Infer size from the literal size (5)
fixed int fa[] = {1, 2, 3, 4, 5};
fb := fixed int[]{1, 2, 3, 4, 5};

Size of an array

The current size of a fixed-sized or dynamic-sized array can be obtained by using the .size()method on the array variable.

ℹ️ The size() method always returns an u64.

a:= int[35];
printf("a's size is: %ld\n", a.size());

Random access and array indexes

Positive array indexes are zero-based, as in C; items can be accessed the same way as in C:

a := fixed int[35];
first := a[0];
third := a[2];

e := a[35];    // compile error: out of bounds access

Unlike C, Nitid allows negative indices which work just as in Python. -1 index represents the last item, -2 the item right before the last, and so on. If an array has N items, negative indices range -N…-1. Any index below -N will raise a compile-time or runtime error.

a := fixed int[5]{1, 2, 3, 4, 5};

last := a[-1];        // last == 5
before_last := a[-2]; // before_last == 4
e := a[-6];           // compile error: out of bounds access

Resizing arrays

A dynamically-sized array can be resized using the resize method, as in the following code sample.

// Initialize arr with a capacity of 25 
arr := [25 i64];

// Resize it to 200
arr.resize(200);

for loop: sequential access

Iterative access is allowed in different ways.

  1. Old style C way

    a := fixed int[35];

// init items

max := cast(a.size(), i8);
for (i8 i = 0; i < max; i++){
  item := a[i];
  // ... do stuff with item
}

  2. Range without index

    a := int[35];

// init items, extend a, etc.

for (item : a){
  // ... item is the same as a[i] in the previous example
}

  3. Range with index

    a := int[35];

// init items, extend a, etc.

for (index,item : a){
  // index is the same as i in the first example
  // item is a[i]
}

Structs

There’s no real OOP in Nitid, but structs are as close as OOP objects as possible.

Structs in Nitid work pretty much as Go structs.

Reserved keywords

Here are the field and method names you must avoid:

  • self refers to the struct which is calling a specific method (like in Python). No members can have this name.
  • bytesize() is a reserved method which calls C’s sizeof() to return the struct size in bytes.

Data members

A struct must contain at least one data member, any type is allowed.

Data members must be declared by specifying their name, followed by a colon (:), their type and a semicolon (;).

Members name must follow identifier syntax, so no initial numeric digits, no punctuation, etc.

struct Person {
  name: string;
  age: u8;
};

Array members

A struct can have any number of array members, declared in either of the following ways.

// C-style array member declaration
struct CacheLine {
  data: u8[64];
};

// Alternate array member declaration
struct CacheLine {
  data: [64 u8];
};

Initialization of array struct members follows the usual way.

c := CacheLine{ data: {1,2,3,4,5} }; // members from the 6th on will be zero-initialized

Methods

Structs in Nitid can have their own methods.

ℹ️ Important: the self keyword denotes the struct which is calling the method, just as in Python. In Nitid, self needs not be declared in the method signature.

struct Circle {
  color: string;
  radius: f32;
};

impl Circle {
  fn greet() -> string {
    return "Hello, I'm " + self.color;
  }
    
  fn area() -> f32 {
    return self.radius * self.radius * 3.14159;
  }
};

Instancing

Struct instances are declared just like scalar or array variables. Data members can be inlined in the declaration.

c := Circle{ color: "red", radius: 1.5 };

Accessing members

Members and methods are referenced using a dot (.) after the variable name.

r := c.radius; // r type is f32
c.greet();     // returns "Hello, I'm red"
c.area();      // returns 7.0685775

Composition / Embedding

A struct can embed another struct anonymously, promoting the inner struct’s fields and methods to the outer one (Go-style composition over inheritance).

struct Employee {
  name: string;
  id: u32;
};

impl Employee {
  fn describe() -> string {
    return "Employee " + self.id + ": " + self.name;
  }
};

struct Manager {
  Employee;        // embedded — no field name
  department: string;
  directReports: u32;
};

impl Manager {
  fn teamSize() -> u32 {
    return self.directReports;
  }
};

Fields and methods of the embedded type are accessed directly on the outer type:

m := Manager{
  Employee: Employee{name: "Alice", id: 1001},
  department: "Engineering",
  directReports: 5,
};

m.name;       // "Alice" — promoted from Employee
m.id;         // 1001   — promoted from Employee
m.describe(); // "Employee 1001: Alice" — promoted method
m.teamSize(); // 5

If the outer struct defines a field or method with the same name, it shadows the embedded one. The embedded field can still be accessed explicitly via its type name:

m.Employee.name; // explicit access, bypasses shadowing

Multiple embedding is allowed. Name conflicts between embedded types produce a compile error.

Method Receiver

In Nitid, self is always a pointer to the receiving struct. No value receiver exists — this avoids implicit copies and makes mutation explicit by default.

#![allow(unused)]
fn main() {
struct Counter {
  value: i64;
};

impl Counter {
  fn inc() {
    self.value = self.value + 1; // mutates through pointer
  }

  fn get() -> i64 {
    return self.value;
  }
};
}

Pointer receiver means the method can modify the struct, and calling a method never copies the struct.

c := Counter{value: 10};
c.inc();
c.inc();
c.get(); // 12

Methods are statically resolved and desugared to plain function calls (Counter_inc(&c)). No dynamic dispatch.

Memory Layout

By default, struct layout follows C ABI rules: fields are aligned to their natural alignment and padding is inserted between fields.

The packed keyword forces the struct to omit padding:

packed struct NetPacket {
  flags: u8;
  length: u16;     // adjacent to flags, no padding
  checksum: u32;   // adjacent to length, no padding
};

Useful for wire protocols, file formats, and hardware registers.

The align(N) attribute sets minimum alignment of the struct as a whole:

align(64) struct CacheLine {
  data: u8[64];
};

Layout attributes compose:

packed align(4) struct Header {
  version: u8;
  kind: u8;
  size: u32;
};

📝 Tags

PLEASE NOTE: struct tags are an unimplemented feature, still in draft status. Do not rely on it yet.

Struct fields can carry arbitrary metadata as string tags, modeled after Go struct tags. Tags are optional string literals following the field type.

struct User {
  name:  string "json:'name' xml:'name'";
  email: string "json:'email,omitempty'";
  age:   u8     "json:'age' validate:'min=0,max=150'";
};

Tags are not interpreted by the language. They are stored as metadata for serialization, validation, ORM mapping, form parsing, and code generation tools.

Enumerations

The enum keyword in Nitid works about the same way as in C++.

The name of both the enum and its members must follow the identifier names rules.

Member values may be declared explicitly; if not declared, values start from 0 and are incremented by 1 at each step.

enums can be untyped, in which case the i32 type will be silently used.

// Implicit i32 type
enum AccessMode {
    NONE = 0, // not needed: 0 is the default start value
    READONLY,
    WRITEONLY,
    READWRITE
};

Or, the enum can be typed explicitly.

// Explicit types
enum ByteAccessMode : u8 {
    NONE,
    READONLY,
    WRITEONLY,
    READWRITE
};

// With signed types, negative values are legal
enum FileType : i16 {
    Error = -1,
    Unknown,
    Jpeg,
    Png,
    Text = 0x1000,
};

In both cases the enum values will be checked at compile time to make sure they fit in the enum type with no overflows.

// 8-bit unsigned int overflow at the second value 
enum Wrong : u8 {
    NONE = 255,
    A_VALUE,
    ANOTHER_VALUE,
};

Caveats

Only integral types are allowed. Trying to use float types, strings or struct types will result in a compile error.

// Error: no float type allowed in enums
enum Wrong : f64 {
    One = 1.0,
    Two,
    Three,
};

// Error: no string/compound type allowed in enums
enum Wrong : string {
    One = "One",
    Two,
    Three,
};

Strings

Nitid provides three string types covering the three Unicode encoding forms:

TypeC typedefEncodingElement widthAccess
stringnitid_stringUTF-81 byte (char)Codepoint via UTF-8 decode
string16nitid_string16UTF-162 bytes (uint16_t)Codepoint via surrogate-pair decode
string32nitid_string32UTF-324 bytes (uint32_t)Direct codepoint lookup

All three store the codepoint count (not byte count) as their length, and support codepoint-indexed access, comparison, and concatenation.

Declaration and initialization

string   s  = "Hello";         // UTF-8 string
string16 s16 = "Hello";        // UTF-16 string (from UTF-8 literal)
string32 s32 = "Hello";        // UTF-32 string (from UTF-8 literal)

// Type inference via :=
t := "world";                  // t is inferred as string (UTF-8)
t16 := "world";                // t16 is inferred as string16
t32 := "world";                // t32 is inferred as string32

String literals are always UTF-8. When assigned to string16 or string32, the runtime converts the literal at initialization time:

  • string16 x = "hi" → nitid_string16_from_utf8("hi")
  • string32 x = "hi" → nitid_string32_from_utf8("hi")

Cross-type assignment is also allowed between string types:

string   s = "hello";
string16 t16 = s;              // OK: string → string16 conversion
string32 t32 = s;              // OK: string → string32 conversion

String literals and Unicode escapes

String literals are enclosed in double quotes ("). The lexer supports C-style escape sequences plus Unicode escapes:

EscapeResult
\nNewline (U+000A)
\tTab (U+0009)
\rCarriage return (U+000D)
\\Backslash
\"Double quote
\'Single quote
\0Null byte
\uXXXXUnicode codepoint from 4 hex digits (U+0000–U+FFFF)
\UXXXXXXXXUnicode codepoint from 8 hex digits (up to U+10FFFF)
 
println("\u0041");                  // A
println("\u00e9");                  // é
println("\u4e2d\u6587");           // 中文
println("\U0001F600");             // 😀

Unicode escapes are decoded in the lexer and stored as the actual UTF-8 bytes in the string literal. The runtime encodes them appropriately for the target string type (surrogate pairs for string16 values above U+FFFF, direct codepoint for string32).

Escape validation

The lexer validates:

  • \u must be followed by exactly 4 hex digits
  • \U must be followed by exactly 8 hex digits
  • Codepoints above U+10FFFF are rejected
  • Lone surrogates (U+D800–U+DFFF) are rejected

Operations

Concatenation (+)

The + operator concatenates two strings of the same type:

string a = "Hello";
string b = " World";
string c = a + b;               // "Hello World"

string16 x = "foo";
string16 y = "bar";
string16 z = x + y;            // "foobar"

Codegen: nitid_string_concat(&a, &b), nitid_string16_concat(&x, &y), etc.

Both operands must have the same string type. string + string16 is a type error.

Comparison (==, !=, <, >, <=, >=)

Comparisons are codepoint-by-codepoint, based on Unicode codepoint numeric values:

string a = "alpha";
string b = "beta";
bool eq  = a == a;             // true  → nitid_string_eq
bool ne  = a != b;             // true  → nitid_string_ne
bool lt  = a <  b;             // true  → nitid_string_lt
bool gt  = b >  a;             // true  → nitid_string_gt
bool le  = a <= a;             // true  → nitid_string_le
bool ge  = b >= a;             // true  → nitid_string_ge

Codegen maps each operator to the corresponding runtime function: nitid_string_eq, nitid_string_ne, nitid_string_lt, etc.

Indexing ([])

String indexing returns the codepoint at the given position as u32:

string s = "Hi 🌍";
u32 cp0 = s[0];                // 'H'  (0x0048)
u32 cp1 = s[1];                // 'i'  (0x0069)
u32 cp2 = s[2];                // ' '  (0x0020)
u32 cp3 = s[3];                // 🌍   (0x1F30D)

Negative indices are supported, counting from the end:

u32 last = s[-1];              // 🌍   (0x1F30D)
u32 prev = s[-2];              // ' '  (0x0020)

Out-of-bounds access returns 0 (the null codepoint).

Codegen:

  • string[n] → nitid_string_at_cp(&s, n)
  • string16[n] → nitid_string16_at_cp(&s16, n)
  • string32[n] → nitid_string32_at_cp(&s32, n)

Printing

The println built-in accepts all three string types:

println("Hello");               // printf("Hello\n") — literal optimization
println(s);                     // printf("%s\n", s.data)
println(s16);                   // converts to UTF-8, then printf
println(s32);                   // converts to UTF-8, then printf
println(s + t);                 // concatenates, prints temp, frees it

For string16 and string32, the runtime converts to a temporary UTF-8 nitid_string, prints its .data, then frees the temporary.

Memory model

Each string type is a heap-allocated struct:

// string   → char   *data, len: size_t, cap: size_t
// string16 → uint16_t *data, len: size_t, cap: size_t
// string32 → uint32_t *data, len: size_t, cap: size_t
  • len is the number of stored units (bytes for UTF-8, uint16_t for UTF-16, uint32_t for UTF-32), NOT the codepoint count.
  • The runtime provides _len() functions (nitid_string16_len, nitid_string32_len) that return codepoint count.
  • Temporary strings (from concat, conversion) are freed automatically by println. User-declared string variables persist for the lifetime of their scope; the generated C code does not free them automatically (no RAII).

    println("\U0001F600");       // 😀
    println("\u00E9");           // é
    println("中文");             // 中文
}

Packages

Nitid code can be organized in packages, which closely resemble Go packages.

A package is a collection of source files containing functions, structures, enumerations, etc. sharing the same logical scope.

Defining packages

To indicate that a source file belongs to a specific package, the first non-comment line of that file must contain the package keyword followed by the package name and a semicolon.

// The file can start with as many comments+whitespace as you like,
// but no valid code must appear before the "package" keyword.
  
package Bubble; // This file belongs to the "Bubble" package.
  
// ... your code

Using packages

In order to make a specific package visible to the Nitid code, the package must be imported using the import keyword followed by the package name, just like this: import PackageName;

Then, everything in the package can be accessed by prepending the package name and a dot (.).

import Bubble; // Make the Bubble package visible here  

// Call the "someFunction" function of the Bubble package  
a := Bubble.someFunction();

// Access the "someVar" variable of the Bubble package
b := Bubble.someVar;

// Access the "SOME_VALUE" variant of the someEnum enum of the Bubble package
c := Bubble.someEnum.SOME_VALUE;

An imported package name can be aliased using the as keyword.

import Bubble as b; // Make the Bubble package visible and alias it to "b"  

// Call the toplevel "someFunction" function of the Bubble package
a := b.someFunction();   

// Error: Bubble is not available since it is aliased to "b"
e := Bubble.someFunction();

Module Layout and Resolution

This document specifies how the compiler locates the source files that make up a package.

Motivation

A package is identified by the package declaration inside each source file, not by its directory. This gives maximum flexibility, but flexibility without any convention creates real costs:

  • Import paths become ambiguous. Without a filesystem convention, the compiler has no way to know where to look for a package’s files short of scanning the entire project tree on every build.
  • Boundaries are unclear. If a directory and its subdirectories can freely belong to the same or to different packages, the compiler needs an explicit rule to decide — otherwise it has to guess.
  • Name collisions are harder to spot. Two files named utils.nt contributing to the same package but sitting in unrelated directories are not obviously related when browsing the filesystem.
  • Incremental builds get more expensive. Dependency tracking has to account for a scattered set of inputs rather than a single directory scan.
  • Refactoring becomes non-local. Moving a file between directories can silently change which package it belongs to, or require updates to configuration living elsewhere.

The goal is to keep the common case (one package, one directory, optionally with subdirectories) free of any extra ceremony, while still allowing a package to span multiple, non-contiguous directories when a project genuinely needs it.

Resolution rules

Package membership is determined by combining the package declaration in each file with the following directory conventions, evaluated in order:

1. Default: directory implies package

A directory containing .nt files is treated as home to the package (s) declared in those files. This is the common case and requires no additional configuration.

2. Subdirectories inherit the parent package

A subdirectory that does not contain its own manifest file is considered part of the same package as its parent directory. This means a package can freely span a directory and its subdirectories without any explicit declaration — the “folder + subfolders” case works out of the box.

mypkg/
  vector.nt      // package mypkg;
  matrix.nt      // package mypkg;
  internal/
    helpers.nt   // package mypkg;  <- inherited, no manifest needed

📝 3. Explicit override: manifest marks a package boundary

PLEASE NOTE: this feature (manifest file, name and syntax) is still in draft status. Do not rely on it yet.

A subdirectory containing its own manifest file (nitid.toml, or a lighter-weight marker such as package.nt) is promoted to an independent package boundary, regardless of what its parent declares. This makes package boundaries locally decidable: to know whether a directory is its own package, it is enough to look inside it — no need to inspect the rest of the tree.

mypkg/
  vector.nt        // package mypkg;
  submodule/
    nitid.toml     // <- presence of manifest makes this its own package
    thing.nt       // package submodule;

4. Multi-directory packages: explicit declaration only

A package that spans multiple, non-contiguous directories is only allowed when declared explicitly in the project’s root manifest, listing the constituent paths or globs:

[package.mypkg]
paths = ["src/mypkg", "vendor/legacy-mypkg", "generated/mypkg/**"]

This keeps the non-contiguous case possible without paying its cost in the common case: it is opt-in, explicit, and centrally visible in the manifest rather than inferred.

Compiler algorithm

Given the rules above, package resolution proceeds as:

  1. Walk the project tree from the root, skipping directories that are covered by an explicit multi-directory declaration in the manifest (rule 4) unless reached as one of their declared paths.
  2. For each directory, determine its owning package: if it defines its own manifest, it starts a new package boundary (rule 3); otherwise it inherits its parent’s boundary (rule 2), with top-level directories defaulting to a package of their own (rule 1).
  3. For every .nt file, verify that its package declaration matches the package owning its directory (per steps 1–2), or the package it was explicitly assigned via a manifest path/glob (rule 4). A mismatch is a compile error.
  4. Group all files by resolved package for the purpose of import resolution, symbol scoping, and incremental build invalidation.

Consequences addressed

  • Import paths stay derivable from the filesystem for the default and inherited cases; only the explicit multi-directory case requires consulting the manifest.
  • Boundaries are locally decidable: the presence or absence of a manifest in a directory is sufficient to answer “is this its own package?”.
  • Name collisions across scattered files remain possible only within the explicitly-opted-in multi-directory case, where the manifest keeps the file set centrally visible.
  • Incremental builds only need to track a scattered input set for packages that declared themselves as such; the common case remains a plain directory scan.
  • Refactoring safety: moving a file within a directory tree that has no manifest boundaries cannot silently change its package. Moving a file across a manifest boundary is a visible, intentional action.

Non-goals

This specification does not address:

  • A remote package registry or version resolution (dependencies are path- or manifest-based only, for now).
  • Automatic detection of accidental multi-directory packages (i.e. two directories declaring the same package name without an explicit manifest entry remain a compile error, not a silent merge).
