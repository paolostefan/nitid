# Pointers and function pointers

Nitid keeps C-style raw pointers, for interoperability (FFI, SDL/GL buffers, ring buffers…). Everything else about
memory — ownership, lifetimes, null-safety — is **not** enforced yet: see [Not supported yet](#not-supported-yet).

Working samples: `samples/pointers.nt`, `samples/nil.nt`, `samples/fn_pointers.nt`.

---

## Address-of and dereference

`&expr` takes the address of a variable or of an array element; `*p` reads (or writes) the pointee.

```nitid
x := 42;
int *p = &x;

println(*p);   // 42
*p = 100;
println(*p);   // 100
```

Deref emits plain C dereference, `*(p)`. Dereferencing a non-pointer is a **semantic** error:

```
In semantic phase, sourcefile.nt:{line}:{column}: pointer type mismatch
```

## Declaring pointers

A pointer type is written `T *`, after the element type. Whether the *pointer itself* may be rebound is chosen at
declaration time:

| Nitid                        | C                | Meaning                              |
|------------------------------|------------------|--------------------------------------|
| `int *p = &x;`               | `i32 *const p`   | pointer is fixed; `*p = …` is fine   |
| `mut int *q = &x;`           | `i32 *q`         | pointer can be re-pointed            |
| `mutable int *q = &x;`       | `i32 *q`         | same as `mut`                        |
| `p := &x;`                   | `i32 *const p`   | inferred: fixed pointer              |
| `mutable base := &arr[0];`   | `i32 *base`      | inferred: rebindable pointer         |

`mut` and `mutable` are synonyms. Pointer types work for scalars and for structs:

```nitid
struct MyStruct { x: i16; name: string; };
ms := MyStruct{ x: 12, name: "Ciao" };
MyStruct *ms_ptr = &ms;   // struct pointers are fine; see the caveat on member access below
```

Several pointers of the same type can share one declaration, but each name needs its own `*`:

```nitid
arr := int[]{10, 20, 30};
mut int *first = &arr[0];
mut int *last = &arr[2];
```

## Pointer arithmetic

`+` and `-` with an integer offset are allowed, and yield another pointer of the same type; comparisons are allowed
too. Both are emitted verbatim to C, so the usual C rules apply — **no bounds checking**:

```nitid
mutable base := &arr[0];
base = base + 1;      // i32 *base = &(((i32 *)arr.data)[0]) + 1
third := base + 2;
println(*third);
```

---

## Pointers to array elements

`&arr[i]` is the way to get a pointer into an array. It transpiles to a plain C address-of on the array's buffer:

```nitid
arr := int[]{10, 20, 30, 40, 50};
mutable base := &arr[0];   // i32 *base = &(((i32 *)arr.data)[0]);
println(*base);            // 10
base = base + 3;
println(*base);            // 40
```

⚠️ The index is **not** checked or normalized here: `&arr[arr.size()]` is accepted, and a negative index such as
`&arr[-1]` is emitted as `[-(1)]`, i.e. a read before the start of the buffer. Negative indexing ("`-1` is the last
item", see [Arrays](3.arrays.md)) is **not implemented** — do not rely on it with or without `&`.

## `nil`

`nil` maps to C `NULL`. Its type is "pointer to void", so it can initialize any pointer declaration:

```nitid
mut int *t = nil;   // i32 *t = NULL
```

There is no `T?` optional type yet, and no null check is generated: dereferencing `nil` is undefined behaviour in the
generated C.

## Function pointers

A function pointer type is declared with `type` + a `fn` signature, and can then be used as a parameter or variable
type:

```nitid
type Cb = fn (int, int) -> int;
```

which transpiles to a plain C typedef:

```c
typedef i32 (* Cb)(i32, i32);
```

Calling through such a variable works, and multi-return signatures work the same way as for normal functions (the
results come back through trailing out-parameters):

```nitid
type Cb = fn (int, int) -> (int, f64);

fn IUseAFunctionPtr(Cb param1) -> (int, f64) {
  a, b := param1(42, 36);
  return a, b;
}
```

⚠️ There is currently **no way to obtain** a function pointer value: naming a function in an expression
(`f(add, 1, 2)`, `Cb f = add;`) is rejected with `Undefined variable 'add'`. Function pointers are therefore only
usable for parameters whose value arrives from the outside — FFI callbacks, or a hand-written C shim. Assigning `nil`
to a function pointer is rejected too.

## Not supported yet

These are current, known gaps — not part of the language contract:

- **Pointers as function parameters.** `fn f(int *p)` does not parse (`Expected identifier, found Star`); a pointer
  return type (`-> int *`) parses but the call site is mistyped, producing broken C.
- **Members through a struct pointer.** `p.field` and `p.method()` are rejected
  (`Cannot access field on non-struct type` / `Cannot call method on non-struct type`). Take `&s` out of the picture,
  or keep a copy of the struct value.
- **No `unsafe` blocks.** Dereferences and FFI calls are not gated behind anything yet, and there is no compile-time
  marker for unsafe code.
- **No const enforcement.** Re-pointing a `T *p` (a C `*const`) is accepted by the transpiler and only rejected by the
  C compiler: `assignment of read-only variable`.
- **No addressability check.** `&42` is accepted and emits `&(42)`, which is not valid C.
- **No pointer-to-pointer**, no casts between pointer types, no `sizeof`/`alignof` builtins.
- **No memory safety.** No bounds checks on pointer arithmetic, no null checks, no ownership or borrow rules; safe
  RAII / reference types are planned for v0.3 (see [ROADMAP](../../ROADMAP.md)).
