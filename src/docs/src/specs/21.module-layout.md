# Module Layout and Resolution

This document specifies how the compiler locates the source files that make up a package.

## Motivation

A package is identified by the `package` declaration inside each source file, not by its directory. This gives maximum
flexibility, but flexibility without any convention creates real costs:

- **Import paths become ambiguous.** Without a filesystem convention, the compiler has no way to know where to look for
  a package's files short of scanning the entire project tree on every build.
- **Boundaries are unclear.** If a directory and its subdirectories can freely belong to the same or to different
  packages, the compiler needs an explicit rule to decide — otherwise it has to guess.
- **Name collisions are harder to spot.** Two files named `utils.nt` contributing to the same package but sitting in
  unrelated directories are not obviously related when browsing the filesystem.
- **Incremental builds get more expensive.** Dependency tracking has to account for a scattered set of inputs rather
  than a single directory scan.
- **Refactoring becomes non-local.** Moving a file between directories can silently change which package it belongs to,
  or require updates to configuration living elsewhere.

The goal is to keep the common case (one package, one directory, optionally with subdirectories)
free of any extra ceremony, while still allowing a package to span multiple, non-contiguous directories when a project
genuinely needs it.

## Resolution rules

Package membership is determined by combining the `package` declaration in each file with the following directory
conventions, evaluated in order:

### 1. Default: directory implies package

A directory containing `.nt` files is treated as home to the package (s) declared in those files. This is the common
case and requires no additional configuration.

### 2. Subdirectories inherit the parent package

A subdirectory that does not contain its own manifest file is considered part of the same package as its parent
directory. This means a package can freely span a directory and its subdirectories without any explicit declaration —
the "folder + subfolders" case works out of the box.

```
mypkg/
  vector.nt      // package mypkg;
  matrix.nt      // package mypkg;
  internal/
    helpers.nt   // package mypkg;  <- inherited, no manifest needed
```

### 📝 3. Explicit override: manifest marks a package boundary

---

A subdirectory containing its own manifest file (`nitid.toml`, or a lighter-weight marker such as
`package.nt`) is promoted to an independent package boundary, regardless of what its parent declares. This makes package
boundaries locally decidable: to know whether a directory is its own package, it is enough to look inside it — no need
to inspect the rest of the tree.

```
mypkg/
  vector.nt        // package mypkg;
  submodule/
    nitid.toml     // <- presence of manifest makes this its own package
    thing.nt       // package submodule;
```

### 4. Multi-directory packages: explicit declaration only

A package that spans multiple, non-contiguous directories is only allowed when declared explicitly in the project's root
manifest, listing the constituent paths or globs:

```toml
[package.mypkg]
paths = ["src/mypkg", "vendor/legacy-mypkg", "generated/mypkg/**"]
```

This keeps the non-contiguous case possible without paying its cost in the common case: it is opt-in, explicit, and
centrally visible in the manifest rather than inferred.

## Compiler algorithm

Given the rules above, package resolution proceeds as:

1. Walk the project tree from the root, skipping directories that are covered by an explicit multi-directory declaration
   in the manifest (rule 4) unless reached as one of their declared paths.
2. For each directory, determine its owning package: if it defines its own manifest, it starts a new package boundary
   (rule 3); otherwise it inherits its parent's boundary (rule 2), with top-level directories defaulting to a package of
   their own (rule 1).
3. For every `.nt` file, verify that its `package` declaration matches the package owning its directory (per steps 1–2),
   or the package it was explicitly assigned via a manifest path/glob (rule 4). A mismatch is a compile error.
4. Group all files by resolved package for the purpose of import resolution, symbol scoping, and incremental build
   invalidation.

## Consequences addressed

- **Import paths** stay derivable from the filesystem for the default and inherited cases; only the explicit
  multi-directory case requires consulting the manifest.
- **Boundaries** are locally decidable: the presence or absence of a manifest in a directory is sufficient to answer "is
  this its own package?".
- **Name collisions** across scattered files remain possible only within the explicitly-opted-in multi-directory case,
  where the manifest keeps the file set centrally visible.
- **Incremental builds** only need to track a scattered input set for packages that declared themselves as such; the
  common case remains a plain directory scan.
- **Refactoring safety**: moving a file within a directory tree that has no manifest boundaries cannot silently change
  its package. Moving a file across a manifest boundary is a visible, intentional action.

## Non-goals

This specification does not address:

- A remote package registry or version resolution (dependencies are path- or manifest-based only, for now).
- Automatic detection of accidental multi-directory packages (i.e. two directories declaring the same package name
  without an explicit manifest entry remain a compile error, not a silent merge).
